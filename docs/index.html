The three practical examples, and what the assistant does well and badly. Each use case can be played in the chat.

The problem

RocketNet's small support team absorbs every customer question — invoices, coverage, faults, installations — over WhatsApp, email and phone. Most repeat what is already published; a few are urgent faults or cancellations hidden behind ordinary wording. The queue is worked in the order it arrives, so the customer about to cancel waits behind someone asking for an invoice copy.

Who uses it

  • Customers — an answer at 21:00 on a Sunday, on WhatsApp or the website, without holding for an agent.
  • Support agents — each ticket arrives with a suggested reply, the account details and a written summary.
  • Operations manager — a daily view of what customers ask and where the assistant had to hand over.

How it works

  1. The customer asks in their own words, on whichever channel they already use.
  2. The assistant reads the intent and pulls out the details: suburb, account, address, package. If a detail is missing it asks, rather than guessing.
  3. It answers only from approved content — packages, the coverage table, the live network status feed and the billing rules.
  4. Six guardrails check the reply before it leaves: approved prices only, no promised installation dates, no account changes without verification.
  5. It answers, books, or hands over to the right team with the whole conversation attached, so the customer never repeats themselves.

Why it is realistic

It is built on content RocketNet already publishes, needs no new hardware, and drops into the WhatsApp and web channels they already run. When confidence is low it degrades to a person instead of inventing an answer. Under POPIA it collects the minimum, verifies identity before any account action, and logs every conversation for review. This prototype runs entirely in a browser with no API keys or live customer data, so it can be shown anywhere — including a classroom with no internet.
